대상 업무와 사용자

  • 사용자: 운영 중인 업무 시스템을 유지보수하는 SI·ITO 개발자
  • 대상 업무: 변경 요청(SR) 처리. MVP는 세 유형만 다룹니다.
    • 결함 수정: 장애 리포트를 보고 원인을 찾아 고침
    • 노후화 대응: 지원 종료 API를 최신 API로 교체
    • 보안 진단 조치: 시큐어코딩 진단 지적 사항 수정

현업의 문제점

  • 결함 원인 위치를 찾느라 로그·코드 검색에 SR당 1~2시간
  • 수정 후 회귀 결함: 고치면서 다른 동작을 깨뜨림
  • 사내 규칙과 과거 유사 장애 조치 이력을 사람이 직접 찾아 대조

수치는 가정치입니다. 근거를 확인한 뒤 교체하세요.

현재 업무 흐름

티켓 접수→ 원인 위치 탐색→ 코드 수정→ 테스트 작성 · 회귀 확인→ 규칙 · 이력 대조→ 승인 · 배포

붉은 단계가 시간이 많이 들거나 결함이 새는 구간입니다.

② 개선 방향 · 기대 효과

해결 아이디어

티켓을 받으면 모델이 고칠 위치를 좁히고, 에이전트가 이력·규칙을 근거로 수정한 뒤, 공격 에이전트가 수정 미달과 회귀를 찾아낼 때까지 검증한다.

스택트레이스는 일부 티켓에만 넣습니다. 항상 있으면 메서드명 일치만으로 거의 다 맞혀서 모델의 의미가 약해집니다.

데이터 누수 방지: 장애·조치 이력 KB와 프롬프트 예시는 학습 분할에서만 만듭니다. 평가 티켓과 E2E 홀드아웃 20건은 KB·예시·과거 결함 수 피처 계산에서 모두 제외합니다.

Agent 구조: 워크플로 그래프

처리 순서(분석 → 수정 → 공격 → 판정 → 승인)가 정해져 있어 Supervisor 대신 고정 워크플로를 씁니다. 역할별로 도구를 나눠 각 에이전트가 볼 도구를 줄였고, 통과 여부는 LLM이 아닌 판정 노드가 결정합니다. 판정에서 실패하면 실패 내용을 붙여 수정 에이전트를 다시 호출합니다.

상태 · 메모리

  • 티켓 상태: ticket_id 단위로 단계, 예측 위치, 패치, 시도 횟수, 실패 목록 보관
  • 장기 메모리: 공격 이력. 다음 티켓에서 같은 유형의 성공 공격을 먼저 시도
  • 에이전트 간에는 대화가 아닌 구조화된 결과(JSON)만 전달

안전장치 (Guard)

  • HITL: 작업본 반영 전 담당자 승인 필수, 반려 시 사유 기록
  • 정답 보호: 에이전트는 기존 테스트와 기대 출력을 수정할 수 없음
  • 실행 격리: 원본은 읽기 전용, 수정은 임시 작업본 디렉터리에서만. subprocess로 실행, 타임아웃 10초
  • 루프 상한: 수정 재시도 3회, 티켓당 토큰 상한

일차작업완료 기준
1일차주문·정산 프로젝트와 pytest 테스트 작성, 실행 도구, 환경 확인(venv·mutmut)run_tests, run_diff 단독 동작

5일차오전: 홀드아웃 20건 E2E·Ablation 배치 실행(전날 밤 시작). 오후: KPI 정리, 발표 준비KPI·Ablation 결과표, 시연 리허설 완료

# RedFix 최종 발표 진행 가이드

발표 자료: `presentation/AI_프로젝트_이종협_수정본.pptx` (10장, 약 11분). 슬라이드마다 발표자 노트에 같은 내용이 들어 있습니다.
시연할 때는 화면이 브라우저로 넘어가 노트를 볼 수 없으니, 이 문서의 **3장 시연 대본**은 출력해서 옆에 둡니다.

**전체 메시지:** RedFix는 담당자를 대신하지 않는다. 근거와 검증 결과를 보여 주고, 담당자가 빠르고 안전하게 결정하게 돕는다.

**이야기 장치 세 개**

| 장치 | 꺼내는 곳 | 회수하는 곳 |
|---|---|---|
| "test / 집가고싶다" 티켓 | 2장 문제 | 시연 ② 접수 검사 |
| "판정은 코드, 승인은 사람" | 4장 전체 흐름 | 시연 ① 공격 로그, 시연 ③ 반려 |
| "모델 순위는 참고, 결정은 근거로" | 6장 모델 | 시연 ① "모델 1위를 고르지 않은 이유" |

## 1. 시간표

| # | 슬라이드 | 시간 | 누적 | 한 줄 핵심 |
|---|---|---|---|---|
| 1 | 표지 | 0:15 | 0:15 | 믿고 승인할 수 있게 만든 SR 에이전트, 마지막은 사람 |
| 2 | 01 문제 | 0:45 | 1:00 | LLM이 고친 코드를 그대로 반영할 수 없는 세 가지 이유 |
| 3 | 02 해결 방향 | 0:45 | 1:45 | 담당자는 찾고 고치는 대신 근거를 보고 결정한다 |
| 4 | 03 전체 흐름 | 1:00 | 2:45 | 분석 → (수정 → 공격 → 판정) 반복 → 승인. 판정은 코드, 막히면 멈춘다 |
| 5 | 04 데이터 | 1:00 | 3:45 | 공개 데이터가 없어 결함을 직접 심고 티켓을 만들었다 |
| 6 | 05 모델 | 1:00 | 4:45 | 순위 학습, 누수 없는 학습 절차, 순위는 참고로만 |
| 7 | **시연** | 3:30 | 8:15 | 승인 / 보완 요청 / 반려 |

| 9 | 07 기획 목표 대비 결과 | 1:15 | 10:30 | 목표 8개 모두 넘음, 두 개는 여유가 작음 (기능별 기여는 말로 설명) |
| 10 | 08 향후 개선과 정리 | 0:30 | 11:00 | 약점은 다음 단계로, 마무리 한 문장 |

**체크포인트:** 시계를 세 번만 봅니다.
- **2:45**에 데이터 장으로 넘어갑니다. 늦었으면 4장은 빨간 화살표와 노란 상자만 말합니다.
- **4:45**에 시연을 시작합니다. 늦었으면 6장은 차트와 "순위는 참고"만 말합니다.
- **8:15**에 시연을 끝냅니다. 늦었으면 8장은 효과 열(초록)만 읽고, 9장의 기능별 기여 설명은 공격 탐지 10/10 한 문장만 남깁니다.

## 2. 슬라이드별 중점

### 1. 표지 (15초)
- **꼭 말할 것:** "제가 가장 신경 쓴 건 잘 고치는 것보다, 담당자가 이 수정을 믿고 승인할 수 있게 만드는 것이었습니다."
- 아래 흐름도의 마지막 "승인 · 사람이 결정"을 가리킵니다. 결과 숫자는 9장에서 처음 공개합니다.

### 2. 문제 (45초)
- 세 장의 카드를 한 문장씩 설명합니다. 근거가 없다 / 회귀 확인은 사람 몫 / 엉뚱한 요청도 고친다.
- **복선:** 3번 카드에서 "실제로 '집가고싶다'라는 장난 티켓을 넣었더니 다른 결함을 고치고 검증까지 통과했습니다. 이 티켓은 시연에서 다시 보여 드리겠습니다."
- "1~2시간"은 기획 단계 가정치입니다. 강조하지 않습니다.

### 3. 해결 방향 (45초)
- **꼭 말할 것:** "진한 칸이 담당자의 일입니다. 위 줄은 전부 사람이 하고, RedFix에서는 등록과 결정만 남습니다."
- **강조:** 아래 노란 상자. "막히면 억지로 고치지 않고 이유를 붙여 넘깁니다."

### 4. 전체 흐름 (1분)
- **여는 말:** "기획 단계부터 이 순서를 고정해 두고, 프레임워크 없이 Python으로 직접 짠 워크플로 그래프로 돌립니다."
- 왼쪽에서 오른쪽으로 손으로 따라가며 노드마다 한 문장씩 말합니다.

| 노드 | 짚을 한 문장 |
|---|---|
| 접수 검사 | "수정 요청인지 LLM이 먼저 보고, LLM이 인용한 증상이 티켓에 그대로 있는지는 코드가 확인합니다." |
| 분석 에이전트 | "예측 모델로 후보를 좁히고, RAG로 사내 규칙 40건과 과거 장애 이력을 찾아 근거를 붙이고, 재현 테스트를 씁니다." |
| 검증 루프 | "고치고(수정), 깨 보고(공격), 코드가 판정합니다. 실패하면 실패 내용을 붙여 수정부터 다시, 최대 3번입니다." (빨간 화살표) |
| 사람 승인 | "통과해도 반영은 담당자가 결정합니다." |

- **가장 힘줘서 말할 것 (회색 상자 첫 줄):** "판정에는 LLM이 없습니다. 기존 테스트 1,145개, 정답 구현과 입력 200개 비교, 공격 에이전트가 낸 입력까지 코드가 직접 다시 실행합니다. LLM이 LLM을 검사하는 구조가 아닙니다."
- **두 번째로 강조할 것 (노란 상자 세 개):** "막히는 곳이 세 군데입니다. 수정 요청이 아니면 보완 요청, 원인을 확신 못 하면 사람 검토, 3번 넘게 실패하면 사람 검토. 억지로 고치지 않습니다."
- 회색 상자 둘째 줄(작업본의 대상 함수만 수정, 테스트 수정 불가, 에이전트별 도구)은 시간 있을 때만 말합니다.
- **넘어가는 말:** "분석 단계의 예측 모델은 데이터부터 직접 만들어 학습했습니다."

### 5. 데이터 (1분)
- **왜 만들었나부터 말합니다:** "'티켓 문장 → 정답 함수' 쌍이 필요한데 공개된 한국어 데이터가 없어서 직접 만들었습니다."
- 위 다섯 칸은 큰 숫자만 따라 읽습니다. 함수 268개 → 두 가지 결함 주입 → 테스트가 깨지는 결함 1,341개 → 티켓 2,678건 → 홀드아웃 20개.
  - AST 뮤테이션은 mutmut이 Windows에서 돌지 않아 직접 구현했다는 점을 한마디 넣습니다.
- **아래 원칙 세 가지가 핵심입니다.**
  - 결함을 직접 심었으니 정답 라벨이 자동으로 정확합니다.
  - LLM에게 결함 코드를 주지 않아 티켓에 원인이 새지 않습니다.
  - 결함 단위로 분할했고, 홀드아웃은 KB·예시·피처 어디에도 안 썼습니다.
- (시간 있으면) "처음엔 함수 108개로 만들었다가 과적합이 나서 2배 넘게 늘렸습니다." 6장 오른쪽 첫 카드와 이어집니다.

### 6. 결함 위치 예측 모델 (1분)
- **문제 정의:** "분류가 아니라 (티켓, 함수) 쌍마다 피처를 계산하는 순위 학습입니다. 그래서 함수 이름이 아니라 판단 패턴을 배웁니다."
- **학습 절차:** "평가 데이터를 보고 모델을 고르지 않게, 하이퍼파라미터는 학습 분할 안에서만 골랐고 평가는 한 번만 봤습니다."
- **결과:** 차트의 0.523 → 0.790 → 0.803.
- **오른쪽 결정 세 가지 (한 문장씩):**
  - 1차 과적합을 대상 확장으로 해결했습니다 (차이 0.165 → 0.02).
  - '과거 결함 수' 피처는 처음 보는 함수에서 0.263으로 무너져 뺐습니다.
  - 트레이스가 없으면 0.779로 약해서, **순위는 참고로만 씁니다.** 시연 ①의 복선입니다.

### 7. 시연 (3분 30초)
- 슬라이드를 10초 띄워 세 장면을 예고한 뒤 브라우저로 넘어갑니다. 진행 내용은 **3장 시연 대본**을 따릅니다.

### 8. 만들면서 바꾼 것 (1분)
- 행마다 "부딪힌 것 → 결정"을 한 문장으로 말하고 효과 열(초록)을 읽습니다.
- **가장 강조할 것:** 첫 행 "누출 2건 → 0건". S2에서 공격이 찾은 시간대 회귀 때문에 판정 1이 실패하고, 재시도해서 통과한 사례입니다.

### 9. 기획 목표 대비 결과 (1분 15초)
- **위 세 줄이 핵심입니다.** "처음 보는 결함 20건 중 19건 해결, 숨긴 테스트로 다시 확인해도 회귀 누출 0건, SR 한 건 평균 약 5분입니다."
- 나머지 초록 세 줄은 한 문장으로 말합니다. "공격 탐지 10건 모두, 근거 인용 100%, 시연 3유형 모두 통과했습니다."
- **노란 두 줄은 먼저 정직하게 말합니다.** "위치 예측 0.803은 목표선 바로 위라 다시 재면 0.80 아래로 나올 수 있고, 예측 도구 기여는 20건 중 1건 차이입니다."
- 티켓당 약 40센트, 못 푼 1건은 시연에서 본 db.query_one입니다.
- **기능별 기여 (슬라이드 없이 말로, 약 30초):** 노란 "예측 도구 기여" 줄과 "공격 탐지율" 줄을 차례로 가리키며 설명합니다.
  - "같은 20건을 기능을 하나씩 끄고 다시 돌렸습니다."
  - 예측 도구를 끄면 해결률이 95% → 90%입니다. 1건 차이라 크게 주장하지 않고, 토큰은 티켓당 약 1.1만 줄었습니다.
  - 공격 단계를 꺼도 이번 20건은 누출 0건이었습니다. 단일 함수 결함이라 기존 테스트로 충분했던 것으로 봅니다. 대신 수정 시도가 0.95회 → 1.15회로 늘었습니다.
  - **강조:** "공격이 필요한 건 테스트가 못 잡는 경우입니다. 기존 테스트로는 안 잡히게 일부러 덜 고친 패치 10건을 공격이 모두 찾았습니다."
- **넘어가는 말:** "그래서 남은 과제는 이렇습니다."

### 10. 향후 개선과 정리 (30초)
- 첫 두 줄만 풀어서 말하고 나머지 세 줄은 빠르게 넘깁니다.
  - 공통 함수 수정: "보신 것처럼 아직 약합니다."
  - 미평가 조건: 다음 과제로 소개합니다.
- **마무리 (천천히):** "RedFix는 담당자를 대신하지 않습니다. 근거와 검증 결과로, 담당자가 빠르고 안전하게 결정하게 돕습니다. 감사합니다."

| 3 | **판정 조건** 탭 → 정답 비교 "미평가" | "시스템이 스스로 '여기는 확인 못 했다'고 알려 줍니다." (시간 없으면 생략) |
| 4 ★ | 요약 탭 **반려** → 사유 입력 → **정답 확인** | 사유: "원인은 공통 조회 함수 db.query_one, 호출부만 감쌈" → "숨긴 테스트 19개가 실패합니다. 담당자의 반려가 맞았습니다." |
| 끝 | — | "자동 검증은 여기까지 해 주고, 나머지는 담당자가 근거를 보고 결정합니다. 그래서 RedFix는 담당자를 대신하지 않습니다." |

### 시간이 모자랄 때 줄이는 순서
1. ①의 3번 (근거·diff)
2. ③의 3번 (미평가 설명)
3. ②와 ③의 ★ 장면은 **끝까지 남깁니다.**

### 문제가 생겼을 때

| 상황 | 대응 |
|---|---|

## 4. 예상 질문과 답

### 데이터

| 질문 | 답 |
|---|---|
| 학습 데이터는 어떻게 만들었나? | 직접 만든 가상 레거시(모듈 20, 함수 268, 테스트 1,145)에 결함을 심었습니다. AST 뮤테이션 11종과 LLM 업무 로직 결함 중 테스트가 깨지는 것만 1,341개 채택했고, 결함마다 LLM이 운영·QA 말투로 티켓 2건을 써서 2,678건입니다 |
| 라벨은 어떻게 붙였나? | 결함을 직접 심었으니 정답 함수를 압니다. 사람이 라벨링하지 않았습니다. 라벨은 줄이 아니라 **함수** 단위이고, 함수 안의 줄은 분석 에이전트가 찾습니다 |
| 티켓에 정답이 새지 않나? | 티켓을 쓰는 LLM에게 결함 diff와 제품 코드를 주지 않고 증상(테스트의 기대값·실제값)만 줬습니다. 제목·본문에 함수명이 있으면 다시 쓰게 했고, 그래도 남은 2개는 뺐습니다. 스택트레이스는 결함 코드가 보이지 않는 형식으로 바꿔, 예외가 난 결함의 QA 티켓에만(15.6%) 붙였습니다 |
| 평가 데이터가 학습에 섞이지 않았나? | 결함 단위로 분할했습니다(학습 1,057 / 평가 262 / 홀드아웃 20). 같은 결함의 티켓은 같은 분할에 있고, 평가·홀드아웃은 이력 KB, 프롬프트 예시, 피처 계산에서 모두 뺐습니다. 분할할 때 누수 검사를 코드로 돌리고, 테스트로도 매번 확인합니다 |
| S1은 학습 데이터 아닌가? | 맞습니다. 이력 검색이 실제 결과를 보여 주게 시연 함수의 결함은 일부러 학습 분할에 넣었습니다. 처음 보는 결함의 증거는 케이스 C와 E2E 20건입니다 |
| 인공 결함이 현실적인가? | 한계입니다. AST 결함은 토큰 하나, LLM 결함도 함수 하나 안에서만 바뀝니다. 그래서 LLM 결함을 섞어 업무 로직 오류를 넣었고(Top-3 0.729로 더 어려움), 여러 파일에 걸친 결함은 다음 단계입니다 |
| 데이터 만드는 데 비용은? | LLM(gpt-6-luna) 비용 약 $0.44입니다 (티켓 작성 $0.33, 결함 주입 $0.11) |

### 모델

| 질문 | 답 |
|---|---|
| 왜 분류가 아니라 순위 학습인가? | 함수 268개를 클래스로 분류하면 함수 이름을 외웁니다. (티켓, 함수) 쌍마다 유사도·트레이스·코드 특성을 계산해 점수를 매기면, 판단 패턴을 배워서 새 함수에도 쓸 수 있습니다. XGBoost Ranker(`rank:ndcg`, LambdaMART)를 썼습니다 |
| 어떤 피처가 중요했나? | 중요도(gain)는 임베딩 유사도 0.72, TF-IDF 0.12, 스택트레이스에 함수가 나오는지 0.08 순입니다. 화면에는 후보마다 SHAP 기여 피처 3개를 보여 줍니다 |
| Top-3 0.803이면 겨우 넘긴 것 아닌가? | 맞습니다. 524건 기준 신뢰구간이 약 ±3.4%p라 목표 수준 달성으로 봅니다. 그래서 순위를 그대로 쓰지 않고 참고 자료로만 씁니다. E2E에서는 모델 Top-3가 85%였고, 에이전트의 최종 위치는 95% 맞았습니다. 무작위로 고르면 3/268 ≈ 1.1%입니다 |
| 처음 보는 함수에도 되나? | 함수 단위 교차검증(평가 함수를 학습에서 통째로 뺌)에서 Top-3 0.774입니다 |
| 과적합은? | 1차(함수 108개, 결함 220개)는 학습 0.941 / 평가 0.776이었습니다. 함수당 결함을 쌓으면 함수를 외우기 때문에, 대상 프로젝트를 2배 넘게 늘리고 함수당 결함을 6개로 제한해 0.825 / 0.803으로 줄였습니다 |
| '과거 결함 수' 피처는 왜 뺐나? | 넣으면 0.845까지 오르지만, 이 데이터는 모든 함수에 결함이 있어서 모델이 "과거 결함 있는 함수 = 정답"으로 배웁니다. 처음 보는 함수에서는 0.263으로 무너졌고, 실제 운영에서는 이력 없는 함수가 대부분이라 뺐습니다 |
| 임베딩 모델은 왜 bge-m3인가? | 다국어 모델이라 한국어 티켓과 영어 코드를 잇습니다. 코드 전용 UniXcoder는 Top-3 0.066으로 무작위 수준이었습니다. 파인튜닝은 하지 않았습니다 |
| 하이퍼파라미터는 어떻게 골랐나? | 8조합을 학습 분할 안에서 결함 단위 5-fold로 비교해 MRR이 가장 높은 것을 골랐습니다(max_depth 4, n_estimators 400, learning_rate 0.05). 평가 분할은 마지막에 한 번만 봤습니다. 시드는 42로 고정해 재현됩니다 |
| 함수 길이 편향은? | 긴 함수일수록 결함 후보가 많아 정답으로 자주 뽑혔습니다(S1의 모델 1위 근거가 "함수 길이"). 함수당 상한 6개, 과거 결함 수 제외로 완화했지만 남아 있는 편향입니다 |

### 에이전트·결과

| 질문 | 답 |
|---|---|
| 예측 도구 +5%p는 1건 차이 아닌가? | 맞습니다. 표본이 작아 크게 주장하지 않고, 평가 세트 확대를 다음 단계로 둡니다. 토큰은 티켓당 약 1.1만 줄었습니다. 예측의 가치는 LLM이 다 읽을 수 없는 큰 코드베이스에서 후보를 줄이는 것이라고 보고 있고, 이 규모에서는 확인하지 못했습니다 |
| 공격을 꺼도 누출 0건인데 공격 에이전트가 필요한가? | 이번 홀드아웃은 단일 함수 결함이라 기존 테스트로 충분했던 것으로 봅니다. 공격은 테스트가 못 잡는 경우를 맡습니다. 기존 테스트로는 안 잡히는 불완전 패치 10건을 10건 모두 찾았습니다(미달 6, 회귀 4) |
| LLM이 틀리게 고치면? | 판정이 코드로 검사합니다. 실패하면 최대 3번 다시 고치고, 그래도 안 되면 사람 검토로 넘깁니다. 판정을 통과해도 마지막은 담당자 승인입니다 |
| 실제 회사에 쓰려면? | 대상 코드, 사내 규칙, 장애 이력을 그 회사 것으로 바꾸고 모델을 재학습합니다. 실제 티켓에는 정답이 없어서 미평가 조건은 담당자가 확인합니다 |
| 비용은? | 티켓당 평균 약 $0.4입니다. 홀드아웃 20건에 $7.76이 들었고, 코드 미리 넣기로 토큰을 39% 줄였습니다 |
| 시연이 녹화본인데 진짜 동작하나? | 실시간 실행은 3~6분이라 녹화했습니다. 녹화본도 실제 실행 기록을 재생한 것이고, 접수 검사는 방금 실시간으로 보셨습니다 |

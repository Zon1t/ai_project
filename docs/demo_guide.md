# RedFix 시연 진행 가이드

> 발표자용. 시연 시간 약 16~19분 기준 (케이스 B·C를 빼면 약 14분). 화면 조작은 모두 브라우저(http://localhost:8501, 같은 네트워크의 다른 기기는 `http://<이 PC IP>:8501`)에서 합니다.

---

## 1. 전날 준비 (30분)

| 확인 | 명령·방법 | 정상 상태 |
|---|---|---|
| 가상환경·의존성 | `.venv\Scripts\Activate.ps1` | 오류 없음 |
| API 키 | 프로젝트 루트 `.env`의 `OPENAI_API_KEY` | 실시간 모드에서 실행 가능 |
| API 크레딧 | OpenAI 결제 화면에서 잔액 확인 | 실시간 1건 약 $0.4~1, 리허설 포함 $5 이상 여유 |
| 검색 색인 | `$env:PYTHONPATH="src"; python -m sr_agent.rag.index` | `data/chroma/` 생성 (처음 한 번, 임베딩 모델 약 2GB 다운로드) |
| 테스트 | `pytest tests` | 모두 통과 |
| 화면 | `streamlit run app/streamlit_app.py` | 재생 모드에 SR-2041·2077·2103이 보임 |
| 실시간 리허설 | 실시간 모드 → SR-2103 → **실행** | 3~4분 안에 "승인 대기" |
| 실시간 비밀번호 (외부 접속을 열어 둘 때) | `.env`에 `REDFIX_LIVE_PASSWORD=<비밀번호>` 추가 후 화면 다시 실행 | 실시간 모드에서 비밀번호를 물음 (재생 모드는 그대로) |

시연 케이스 A~D도 리허설로 한 번씩 실행해 두고, 재생 데이터로 녹화합니다 (실시간이 잘 안 될 때 재생 모드에서 같은 장면).

```powershell
$env:PYTHONPATH = "src"
python -m sr_agent.ui save-replay DEMO-A DEMO-B DEMO-C DEMO-D
```

리허설로 실행한 실시간 결과는 `runs/`에 남습니다. 시연 당일 실시간으로 다시 보여 주려면 **처음부터 다시**를 켜고 실행합니다.

**재생 데이터를 새로 녹화하려면** (실시간 결과가 더 좋게 나왔을 때):

```powershell
$env:PYTHONPATH = "src"
python -m sr_agent.run --ticket SR-2103 --restart
python -m sr_agent.ui save-replay SR-2103
```

## 2. 시연 순서

시연은 두 부분입니다.

| 부분 | 티켓 | 보여 주는 것 | 학습 데이터와의 관계 |
|---|---|---|---|
| 흐름 | S1~S3 (SR-2041·2077·2103) | 분석 → 수정 → 공격 → 판정 → 승인이 실제로 어떻게 도는지, 근거(이력·규칙) | 시연 대상 함수의 결함은 **학습 분할에만** 넣었다 (PRD 5장). 이력 검색이 실제 결과를 보여 주게 하려는 것으로, "처음 보는 결함"의 증거는 아니다 |
| 판단 | 시연 케이스 A~D (DEMO-A~D) | **발표자가 직접** 코드를 보고 승인·반려하고, 정답 확인으로 판단이 맞았는지 본다 | A~C는 학습·이력 KB에 **없는** 홀드아웃 결함, D는 정답 자체가 없는 새 티켓 |

| 케이스 | 상황 | 발표자가 할 판단 |
|---|---|---|
| A `payment.mask_card_number` | 깔끔히 통과 | 수정 전/후 코드를 보고 승인 |
| B `review.calc_average_rating` | 통과했지만 계산식 수정 | 바뀐 식을 직접 읽고 승인·반려 |
| C 공통 함수 `db.query_one` 결함 | 녹화본: **판정은 통과**했지만 호출하는 쪽 `coupon.find_coupon`만 감쌈 (실행할 때마다 사람 검토로 멈출 수도 있음) | 결함 위치·이유를 읽고 "원인은 공통 함수"임을 짚어 반려 → 정답 확인에서 숨긴 테스트 19개 실패 |
| D `customer_dao.find_by_email` 보안 | 정답 구현 없음 → 일부 판정 조건 미평가 | 미평가 안내를 보고 코드를 직접 확인한 뒤 승인·반려 |

실시간 실행은 3~6분 걸리므로 **시연 시작 직후 다른 브라우저 탭에서 먼저 눌러 두는 것**을 권합니다.

### 0단계 · 시작 전 (1분)

1. 브라우저 탭 두 개를 엽니다.
2. **탭 B**: 모드 **실시간** → 사이드바 **시연 케이스 불러오기** → **A** → **불러오기** → **실행**. 그대로 둡니다.
   - 실행을 미리 해 둔 경우(리허설 결과가 있음)에는 **처음부터 다시**를 켜고 실행합니다.
3. **탭 A**: 모드 **재생**. 여기서 발표를 진행합니다.

### 1단계 · 문제 소개 (1분)

- "운영 SR 한 건에 원인 찾기·회귀 확인·근거 대조로 1~2시간이 듭니다."
- 오른쪽 위 **사용 설명서**를 잠깐 열어 단계 표(분석 → 수정 → 공격 → 판정 → 승인)를 보여 주고 닫습니다.
- 강조점: **통과 여부는 LLM이 아니라 코드가 판정**하고, 반영은 사람이 승인합니다.

### 2단계 · S1 결함 수정 — SR-2041 (4분)

1. 사이드바에서 **SR-2041** 선택 → **진행 과정 재생**.
   - 진행 막대 한 줄과 단계 배지가 바뀌는 것을 보여 줍니다 (약 10초).
2. 끝나면 펼쳐지는 **처리 과정** 표: 분석 → 수정 → 공격 → 판정 단계별 LLM 턴·도구 호출. 처리 시간은 화면에서 뺐으니 6단계 KPI 표에서 말합니다 (목표 15분 이내).
3. 판정 제목 아래 **한 줄 요약**: "재시도 n회 · 공격이 제기한 문제 n건 → 판정이 다시 실행해 실제 문제 n건". **판정 조건 보기**를 펼치면 조건마다 무엇을 확인했는지(재현 테스트·기존 테스트 1,145개·변경 범위·정답 비교·공격 결과 재확인)가 묶음별로 나옵니다.
4. **결함 위치** 탭이 핵심 장면입니다.
   - 모델 1위는 `discount.is_coupon_applicable`(쿠폰 조건 판단), 에이전트는 원인 함수 `discount.apply_coupon`(모델 2위)를 골랐습니다.
   - **모델 1위를 고르지 않은 이유**를 펼쳐 읽어 줍니다. "예측은 참고 자료, 최종 판단은 근거로."
5. **근거** 탭: `BIZ-CPN-01`·`BIZ-CPN-02` 규칙 → "사내 규칙을 인용해서 고쳤다."
5-1. **패치 diff** 탭 → **나란히**: 왼쪽 수정 전, 오른쪽 수정 후 `apply_coupon` 전체 코드.
   **바뀐 줄 표시**로 바꾸면 한 화면에서 초록(+)·빨강(-)으로 바뀐 줄 4개만 보입니다.
   - "최소 주문 금액 판단을 직전 쿠폰 적용 후 금액으로(BIZ-CPN-01), 결과에 0원 하한(BIZ-CPN-02) — 딱 두 군데만 고쳤습니다."
6. **공격 로그** 탭: 공격이 제기한 입력마다 **판정 결과** 열(실제 문제 / 문제 아님)이 있습니다. 공격이 "미달"이라고 주장해도 판정이 정답과 같다고 확인하면 "문제 아님"입니다.
   - "LLM은 입력만 제안하고, 맞고 틀림은 코드가 다시 실행해서 정합니다."

### 3단계 · S2 코드 표준화 — SR-2077 (3분)

이 시나리오는 **공격이 문제를 찾아 재시도하는 흐름**이 실제로 나온 사례입니다.

1. **SR-2077** 선택 → 재생.
2. 처리 과정 표: 수정 1 → 공격 1 → **판정 1 실패** → 수정 2 → 공격 2 → 판정 2 통과.
3. **공격 로그** 탭 → 시도 선택에서 **시도 1 실패**: 시간대가 붙은 입력(`2024-03-31T10:00:00+00:00`)에서 원본과 결과가 달라진 회귀 2건, 판정 결과 "실제 문제".
   - 시도 2의 요약 줄: "이전 시도 판정 실패 → 문제를 찾았던 관점(경계값·타입·빈 값) + 새 관점(조합·순서)". 재시도는 의심스러운 관점에 집중해 3라운드만 돕니다.
4. **시도 2 통과**로 바꾸고 **패치 diff** 탭에서 `datetime.utcnow`·`pytz` → `datetime.now(timezone.utc)`·`zoneinfo` 교체를 보여 줍니다.

### 4단계 · S3 보안 조치 — SR-2103 (2분)

1. **SR-2103** 선택 → 재생 (짧게).
2. **패치 diff**: f-string SQL → `?` 파라미터 바인딩. **근거** 탭의 `SEC-SQL-01`.
3. **판정 조건 보기** → 정답·원본과 비교 묶음의 "공격 입력 무력화": 인젝션 입력 4종을 막았는지 코드로 확인.

### 4-1단계 · 엉뚱한 티켓은 받지 않음 — 접수 검사 (1분)

1. 탭 B(실시간)에서 **새 티켓 등록** → 유형 결함 수정, 제목 `정산 문의`, 본문 `정산 관련해서 확인 부탁드립니다.` → **등록** → **실행**.
2. 수 초 안에 **보완 요청**: "시스템 수정 요청으로 볼 수 없음 · 증상 문장을 찾지 못함"과 보충할 정보가 나옵니다.
   - "말이 안 되는 티켓으로 다른 결함을 억지로 고치는 일을 막습니다. LLM이 판단해도, 인용한 증상이 티켓에 실제로 있는지는 코드가 확인합니다."
   - 본문이 8자 미만이면 등록할 때 바로 막힙니다 (LLM 호출 없음).
3. 보여 준 뒤 실행 버튼 줄 오른쪽 **삭제**로 지웁니다.

### 5단계 · 발표자가 직접 판단 — 시연 케이스 (5분)

여기부터는 "도구가 고친 것을 **사람이 어떻게 판단하는지**"를 보여 줍니다.

1. **탭 B**(실시간, 케이스 A)로 이동합니다. 끝났으면 "승인 대기"와 처리 과정 요약이 보입니다.
   - 화면 위 **시연 케이스 A** 상자에 "확인할 것" 3가지가 있습니다. 그대로 따라 확인합니다.
   - "이 결함은 모델 학습에도, 과거 이력에도 없던 결함입니다."
2. **결함 위치** 탭 → **이 함수의 현재 코드(수정 전)**를 펼쳐 결함 코드를 보여 줍니다.
3. **패치 diff** 탭 → **바뀐 줄 표시**: 연산자 하나만 바뀐 것을 확인합니다.
4. **승인 후 반영** → 맨 아래 **정답 확인**.
   - 숨겨 둔 정답 테스트를 패치에 돌려 "담당자 판단이 정답과 맞습니다"가 뜹니다.
5. 시간이 있으면 **C**(재생 모드의 DEMO-C 권장)를 보여 줍니다. **판정 통과가 곧 정답은 아니라는 장면**입니다.
   - 결함 위치 탭의 에이전트 판단 이유: "`db.query_one`은 결과가 없으면 `{}`를 반환" — 원인을 알고도 패치는 `coupon.find_coupon`만 감쌌습니다.
   - 판정 조건 보기: 정답과의 Hypothesis 비교가 **미평가**(입력 규칙 없음)라 판정이 잡지 못했습니다.
   - **반려** → 사유("원인은 공통 조회 함수 db.query_one, 호출부만 감쌈") → **정답 확인**: 숨긴 테스트 19개 실패, "담당자 판단(반려)이 정답과 맞습니다".
   - 실시간으로 돌리면 사람 검토로 멈추기도 합니다(E2E 3조건 모두 그랬음). 그때는 사유를 읽고 반려하면 됩니다.
6. 마지막으로 **D**: "정답이 없는 진짜 새 티켓"입니다.
   - 판정 위 **자동으로 확인하지 못한 조건** 안내를 보여 줍니다. "자동 검증은 여기까지, 나머지는 담당자가 봅니다."
   - 패치 diff에서 `?` 바인딩으로 바뀐 것을 직접 확인하고 승인합니다. 정답 확인은 "정답 없음 — 담당자 판단이 최종".

케이스 B는 질문이 "숫자 계산도 믿을 수 있나?"로 오면 꺼냅니다 (평균 식을 직접 읽고 판단).

### 6단계 · 성과 정리 (2분)

`eval/results/kpi_ablation_v12.md`의 표를 보여 줍니다 (5일차 결과는 `kpi_ablation.md`).
- KPI 8개 모두 달성: E2E 해결률 19/20, 회귀 누출 0건, 공격 탐지율 10/10, 예측 도구 기여 +5%p, 5일차 대비 토큰 -39%.
- 처리 시간: S1 4.9분, S2 8.3분, S3 2.8분 (목표 15분).
- 한계도 함께 말합니다: 새로 등록한 티켓은 정답 구현이 없어 일부 조건이 "미평가"로 표시되고, 그때는 사람이 직접 확인합니다(사용 설명서 6장).

## 3. 문제가 생겼을 때

| 상황 | 대응 |
|---|---|
| 진행 막대가 "크레딧 소진"으로 멈춤 | 재생 모드로 계속 진행 (재생은 API를 쓰지 않음) |
| 실시간 실행이 오래 걸림 / API 오류 | 탭 B는 두고 재생 모드로 계속 진행. 마지막에 "리허설 결과"로 `runs/`에 남은 상태를 보여 줌 |
| 실시간 결과가 "사람 검토" | 오히려 장면으로 씁니다: 위쪽 경고의 사유와 판정 조건을 보여 주고 "통과 못 하면 사람에게 넘긴다"를 설명 |
| 케이스 C가 사람 검토로 멈춤 / 통과함 | LLM은 매번 조금 다르게 풉니다. 어느 쪽이든 패치가 공통 함수(`db.query_one`)를 고쳤는지 보고 판단 → 정답 확인 |
| 케이스 결과가 리허설과 다름 | 재생 모드의 **DEMO-A~D**(리허설 녹화본)로 같은 장면을 보여 줍니다 |
| 재생 중 승인을 눌러 버림 | **승인·반려 기록 초기화** |
| 화면이 안 뜸 | 터미널에서 `streamlit run app/streamlit_app.py` 다시 실행 |
| 실시간 실행 중 다른 티켓을 봐야 함 | 그대로 옮겨도 됩니다. 실행은 서버에서 계속되고, 그 티켓을 다시 열면 진행 화면 → 끝나면 결과 |
| 리허설 결과를 지우고 싶음 | 실행 버튼 줄 오른쪽 **삭제**, 여러 개는 사이드바 **결과 정리** |

## 4. 예상 질문

| 질문 | 답 |

## 2. 실패 원인별 보완

5일차 Ablation에서 해결하지 못하거나 누출된 티켓을 원인별로 나눴다.

| 티켓 (조건) | 원인 | 보완 | 기대 효과 |
|---|---|---|---|
| `review.can_write_review` (전체, 3회째 통과 후 누출) | 1회째 공격 입력을 3회째 판정이 다시 실행하지 않음 | 판정이 이전 시도 공격 입력까지 누적 재실행 (`graph.judge_attack_inputs`) | 같은 입력으로 되돌아간 패치는 판정 실패 |
| `tax.split_mixed_items` (전체·예측 끔, 누출) | 숨긴 테스트의 입력을 판정이 보지 못함 (같은 원인 가능성) | 위와 같음. 재측정으로 확인 필요 | 확인 필요 |
| `shipping.decide_return_fee_payer` (3조건 모두 분석 실패) | `read_method`가 함수만 보여 줘 분기 기준 상수(`SELLER_FAULT_REASONS`)를 모름 → 재현 테스트에 `"상품 불량"` 같은 지어낸 사유 코드 | `read_method`가 참조 모듈 상수를 함께 반환, 분석 프롬프트에 "입력값을 지어내지 않는다" 추가 | 코드에 있는 `"DEFECT"` 등을 사용 |
| `settlement.settle_order` (전체, 분석 실패) | 재현 테스트가 결함 동작(`> expected`)을 단언 | 프롬프트에 이미 "올바른 동작을 기대" 규칙 있음. 이번에는 미반영 | 재측정 후 판단 |
| `test_e2e.py` 2건 (이 PC) | clone 시 `autocrlf=true`로 대상 코드가 CRLF → 결함 데이터 해시 불일치, OneDrive 읽기 전용 폴더 | 저장소 `core.autocrlf=false`, 줄바꿈 LF 복원, `remove_tree` | 통과 |

## 2-1. 실제 재실행으로 확인 (API, 2026-10-21 밤)

검색 색인을 만들고(이력 1,057건, 규칙 40건) 5일차 실패·누출 티켓 4건을 다시 돌렸다 (`python -m eval.run_e2e --only ... --tag recheck`).
돌리면서 새로 드러난 원인을 고치고 그 티켓만 다시 돌렸다.

| 티켓 | 5일차 | 1차 재실행 | 새로 드러난 원인 → 보완 | 최종 |
|---|---|---|---|---|
| `settlement.settle_order` | 분석 실패 | ✅ 해결 | — | ✅ 숨긴 테스트 통과 |
| `shipping.decide_return_fee_payer` | 3조건 모두 분석 실패 | ✅ 해결 | (모듈 상수 반환 효과) | ✅ 숨긴 테스트 통과 |
| `review.can_write_review` | 판정 통과 후 **누출** | 판정이 막음 → 토큰 상한 | 결함이 지운 반환 코드 `"EXPIRED"` 대신 `"PERIOD_ENDED"`를 지어냄 → 같은 뜻의 기존 코드를 따르게 지침·피드백 | ✅ 숨긴 테스트 통과 |
| `tax.split_mixed_items` | 판정 통과 후 **누출** | 분석 실패 | ① "알 수 없는 유형"을 키 누락으로 만들어 기본값이 적용됨 → 재현 실패 피드백에 "입력을 의심하라" ② 함수 전체를 다시 써서 `None` 처리가 바뀜 → 최소 변경 원칙 ③ 티켓 상황(면세 혼합)일 때만 고침 → 티켓 상황으로 범위를 좁히지 않기, 공격은 조건이 거짓인 입력도 | 판정 통과 후 누출 1건 → ③ 보완 후 전체 재측정에서 확인 |

실제 실행 중 발견한 도구 문제: S2 재시도 패치에서 같은 import가 두 줄씩 들어감 → `apply_patch`가 이미 있는 import는 다시 넣지 않음.
S3를 실시간으로 다시 돌려(227초, 1회째 통과) 패치 설명 본문에 규칙 ID가 들어간 결과로 재생 데이터를 다시 녹화했다.

## 2-2. 전체 재측정 (진행 중, API 크레딧 소진으로 중단)

보완을 모두 반영하고 3조건을 다시 돌렸다 (조건마다 `run_e2e --workers 2`, 별도 프로세스로 동시 실행).
도중에 OpenAI API 크레딧이 소진돼 중단했다. 끝난 티켓만 집계한 결과:

| 조건 | 끝난 티켓 | 이번 | 5일차 (같은 티켓) |
|---|---|---|---|
| 공격 끔 (no_attack) | **20/20 완료** | 해결 **19/20 (95%)**, 숨긴 테스트까지 19, 누출 **0**, $3.60, 평균 217초 | 해결 16/20, 숨긴 테스트까지 15, 누출 1, $5.19 |
| 전체 기능 (full) | 12/20 | 해결 12/12, 숨긴 테스트까지 12, 누출 0, $4.72 | 해결 12, 숨긴 테스트까지 11, 누출 1 |
| 예측 끔 (no_predict) | 11/20 | 해결 11/11, 숨긴 테스트까지 11, 누출 0, $4.59 | 해결 10, 숨긴 테스트까지 10 |

- `eval/results/e2e_no_attack.*`은 이번 결과로 바뀌었고, `e2e_full.*`·`e2e_no_predict.*`·`kpi_ablation.*`은 아직 5일차 결과다.
- 남은 티켓(full 8건, no_predict 9건, 약 $7~8)은 크레딧을 충전한 뒤 같은 명령으로 이어서 돌린다. 끝난 티켓은 다시 돌리지 않는다.
  ```powershell
  $env:PYTHONPATH = "src"
  python -m eval.run_e2e --split holdout --workers 2                 # full
  python -m eval.run_e2e --split holdout --workers 2 --no-predict    # no_predict
  python -m eval.run_ablation --report-only                          # KPI 표 갱신
  ```

이번 재측정에서 드러난 견고성 문제:

| 상황 | 전 | 후 |
|---|---|---|
| API 시간 초과·서버 오류 (SDK 재시도 뒤) | 예외가 그대로 올라가 **배치 전체가 중단** (full 조건이 12건에서 멈춤) | 이 티켓만 사람 검토(`LLMError`), 배치는 계속 |
| 크레딧 소진 (429 insufficient_quota) | 위와 같음 | `LLMQuotaExceeded`로 즉시 멈추고 상태를 "끝남"으로 기록하지 않음 → 충전 후 이어서 실행 |
| API 시간 초과 기준 | 120초 | 300초 (추론 high 응답이 길어 정상 응답도 끊김) |

## 3. 새 결함·새 코드에 대한 동작 (질문 정리)

- **결함 위치 예측**은 결함 패턴을 외운 모델이 아니다. 피처가 티켓-코드 유사도(TF-IDF·bge-m3), 스택트레이스 일치, 함수 길이·복잡도라, 학습에 없던 결함과 새로 추가된 함수에도 점수를 매긴다. "과거 결함 수"는 주 모델에서 이미 뺐다 (처음 보는 함수에서 Top-3 0.775 → 0.295로 무너짐).
- 예측은 참고 자료이고, 분석 에이전트(LLM)가 코드·호출 관계·이력·재현 테스트로 최종 위치를 정한다. 홀드아웃 20건에서 모델 Top-3 85%, 에이전트 최종 위치 100%.
- **한계**: 화면에서 새로 등록한 티켓은 정답 구현이 없어, 판정의 "정답 구현과 동일(Hypothesis)"·"공격 입력 재판정"이 미평가다. 이때 통과 여부는 재현 테스트·기존 테스트·변경 범위로만 정해지므로, 화면이 미평가 조건을 알리고 승인 전 직접 확인하게 했다. 사용 설명서 6장.
- **다른 프로젝트**에 쓰려면 `target/` 교체 후 사내 규칙·이력 색인을 다시 만들고 모델 재학습을 권장한다.

## 1. 한눈에 보기

### 1.1 왜 이 작업을 하나

SR 에이전트의 첫 단계는 "티켓에 적힌 증상을 보고 어느 함수가 고장 났는지 좁히는 것"이다.
이걸 도와줄 **결함 위치 예측 모델**을 만들려면 "티켓 문장 → 정답 함수" 쌍이 많이 필요한데, 공개된 한국어 데이터가 없다.
그래서 데이터를 직접 만들었다. 정상 코드에 결함을 심고, 테스트로 진짜 고장 난 버전만 고르고, LLM에게 그 증상을 현업 티켓처럼 쓰게 했다.
결함을 우리가 심었으므로 정답(어느 함수인지)은 사람이 라벨링하지 않아도 정확하다.

## 2. 대상 프로젝트 확장

처음에는 1일차 프로젝트(함수 108개)로 데이터를 만들었다. 그런데 결함을 넣을 수 있는 자리가 348개뿐이라 결함 220개, 평가 티켓 76건밖에 나오지 않았고, 모델이 과적합됐다 (8장).
결함을 더 넣으려면 함수 하나에 결함을 여러 개 쌓아야 하는데, 그러면 모델이 "자주 고장 나는 함수"를 외우게 된다.
그래서 **함수 자체를 늘리는 쪽**을 택했다 (사용자 승인). 기존 12개 모듈과 테스트는 한 줄도 바꾸지 않았다.

| 추가 모듈 | 업무 | 예 |
|---|---|---|
| `shipping` | 배송 | 지역·도서산간 배송비, 운송장 체크디지트, 배송 상태 전이, 도착 예정일 |
| `inventory` | 재고 | 가용 재고, 예약·해제, 안전재고 경고, FIFO 로트 출고 |
| `point` | 포인트 | 등급별 적립, 100원 단위 사용, 365일 만료, 환불 시 회수 |
| `promotion` | 프로모션 | 타임세일가, N+1 증정, 묶음 할인, 중복 불가·최대 혜택 선택 |
| `notification` | 알림 발송 | SMS/LMS 구분(90바이트), 야간 광고 발송 제한, 채널 선택, 재시도 |
| `tax` | 세금·영수증 | 공급가·세액 분리, 현금영수증 대상, 사업자번호 검증, 신고 기한 |
| `review` | 상품 리뷰 | 작성 가능 기간, 평균 평점 반올림, 포토 리뷰 적립, 신고 블라인드 |
| `seller` | 판매자 관리 | 등급 산정, 정산 보류, 휴면 판단, 패널티·제재 단계 |

- 모듈마다 함수 20개, 기존 코드와 같은 레거시 스타일(`%` 포맷, `# type:` 주석)로 썼다.
- 새 모듈에는 일부러 넣은 결함이나 지원 종료 API(`utcnow`, `pytz`)가 없다. S1~S3 시연 재료와 섞이지 않게 하려는 것이다.
- 테스트는 모든 함수의 경계값 양쪽을 검사한다. **결함을 심었을 때 테스트가 실패해야 그 결함을 데이터로 쓸 수 있기 때문**이다.

## 3. 결함 주입과 선별 (F2-1, F2-2)

### 3.1 AST 뮤테이션

코드를 파싱해(AST) 연산자·상수 같은 토큰 하나를 바꾸는 방식이다. 원래 PRD는 mutmut을 쓰려 했지만 Windows에서 동작하지 않아 직접 만들었다 (`datagen/mutate.py`).

| 연산자 | 바꾸는 것 | 예 | 채택 |
|---|---|---|---|
| ROR | 비교 연산자 (경계값 실수) | `<` → `<=`, `==` → `!=` | 131 |
| ARG | 호출 인자 순서 | `g(a, b)` → `g(b, a)` | 134 |
| CRP | 숫자·불리언 상수 | `100` → `101`, `True` → `False` | 123 |
| NEG | 조건 부정, `not` 제거 | `if x:` → `if not x:` | 115 |
| AOR | 산술 연산자 | `+` → `-`, `*` → `//` | 95 |
| RSD | `raise`·가드 `return` 삭제 (검증 누락) | `raise ValueError(...)` → `pass` | 91 |
| MCR | 감싼 호출 제거 (절사·변환 누락) | `round_down_won(x)` → `x` | 47 |
| SDL | 문장 삭제 (갱신 누락) | `order["items"] = ...` → `pass` | 46 |
| SCR | 상태 코드 문자열 | `"PAID"` → `"SHIPPED"` | 43 |
| LCR | 논리 연산자 | `and` ↔ `or` | 19 |
| MMR | `max` ↔ `min` (상·하한 실수) | `max(0, x)` → `min(0, x)` | 9 |

만드는 방식의 특징:

- **바뀐 토큰만 갈아 끼운다.** 파일을 통째로 다시 쓰지 않으므로 diff가 한 줄이고 주석·포맷이 그대로다.
- **바꾼 뒤 다시 파싱해서 검사한다.** 의도한 노드 하나만 바뀌었는지 확인하고, 아니면 버린다.
- **바꾸지 않는 곳:** docstring, f-string 내부, `print`·로그 호출, 기본 인자값, 데코레이터, 함수 밖 코드. 바꿔도 테스트가 잡지 못하거나 모듈 import 자체가 깨지는 곳이다.
- 한글이 섞인 줄에서 위치가 어긋나지 않도록 UTF-8 바이트 위치를 문자 위치로 변환한다.

### 3.2 LLM 결함 주입

AST 뮤테이션은 토큰 하나만 바꾸므로 "업무 로직을 잘못 이해한" 결함은 만들지 못한다. 그래서 함수마다 LLM(gpt-6-luna)에게 실제 개발자가 낼 법한 결함 4개를 제안받았다 (`datagen/llm_inject.py`, 프롬프트 `datagen/prompts/bug_injector.md`).
LLM의 제안은 그대로 쓰지 않고 **코드로 검증**한다.

| 검사 | 버린 수 |
|---|---|
| 바꿀 코드 조각이 함수 안에 정확히 한 번 나오는가 | 14 |
| 바꾼 파일이 문법 오류 없이 파싱되는가 | 2 |
| AST가 실제로 달라졌는가 (공백·괄호만 바뀐 것 제외) | 2 |
| AST 결함과 결과 파일이 같지 않은가 (중복) | 87 |

제안 1,033개 중 928개가 통과했다. 예시 (실제 채택된 결함):

```diff
# order.change_status — [상태 전이 검증 기준 오류] 현재 상태가 아니라 요청된 새 상태를 기준으로 전이 규칙을 확인
-    if new_status not in VALID_TRANSITIONS.get(order["status"], []):
+    if new_status not in VALID_TRANSITIONS.get(new_status, []):
```

### 3.3 테스트로 선별

후보마다 임시 작업본에 결함을 심고 대상 프로젝트 테스트 1,145개를 돌린다 (1일차의 `run_tests` 도구를 그대로 사용, 작업본 6개 병렬).

| 결과 | 개수 | 처리 |
|---|---|---|
| 테스트 1개 이상 실패 (killed) | 1,341 | **채택** |
| 모든 테스트 통과 (survived) | 165 | 버림. 동작이 같거나 테스트가 못 잡는 결함 |
| 타임아웃 (10초) | 7 | 버림. 무한 루프 |
| 같은 배치에서 함수 상한 초과 | 6 | 버림 |

- **함수당 상한:** AST 4개 + LLM 2개 = 최대 6개. 특정 함수에 결함이 몰리지 않게 하려는 것이다.
- 후보 순서는 시드(`config.SEED = 42`)로 섞고 함수를 돌아가며 고른다. 같은 코드·시드면 같은 결과가 나온다.
- 결과: 함수 268개 모두 결함이 있다. 결함 6개인 함수 158개, 5개 33개, 4개 21개, 3개 37개, 2개 14개, 1개 5개.
- 후보 1,519개를 검사하는 데 약 23분 걸렸다. `target/` 원본 해시는 실행 전후 같았다.

## 4. 티켓 작성 (F2-3)

### 4.1 방식

결함 1개마다 LLM(gpt-6-luna)을 한 번 호출해 작성자가 다른 티켓 2건을 받는다 (`datagen/tickets.py`, 프롬프트 `datagen/prompts/ticket_writer.md`).

| 티켓 | 작성자 | 내용 |
|---|---|---|
| A | 운영 담당자 | 업무 용어로 겪은 증상만 |
| B | QA 담당자 | 재현 조건, 기대 결과, 실제 결과 |

- **LLM에게 주는 것:** 업무 영역(모듈 설명 한 줄), 실패 테스트 수, 테스트 쪽 실패 정보(호출과 기대값·실제값).
- **주지 않는 것:** 결함 diff, 제품 코드 소스. 원인을 알면 티켓에 원인을 써 버리기 때문이다.
- **코드로 하는 검사:** 제목·본문에 정답 함수명(`apply_coupon`, `discount.apply_coupon`)이나 snake_case 식별자가 있으면 위반 내용을 붙여 1회 재시도한다. 그래도 남으면 그 결함은 뺀다 (2개 제외 → 1,339개).
- 응답은 결함 단위로 바로 `drafts.jsonl`에 저장한다. 중간에 끊겨도 이어서 실행하고, 이미 만든 결함은 다시 호출하지 않는다.

### 4.2 스택트레이스

PRD는 "스택트레이스는 일부 티켓에만"을 요구한다. 처음에는 결함마다 포함 1건·미포함 1건으로 하려 했지만 두 가지 문제가 있었다.

1. **pytest 출력에는 결함 코드가 그대로 찍힌다.** 실패한 함수의 소스 전체를 보여 주기 때문이다. 이걸 붙이면 정답을 알려 주는 셈이다.
2. **값만 틀린 결함은 운영에서도 traceback이 없다.** 예외 없이 9,900원이 나와야 할 곳에 10,000원이 나오는 결함은 로그에 아무것도 남기지 않는다.

그래서 `datagen/traces.py`가 pytest 출력을 **실제 Python traceback 형식**(파일·줄·함수·실패한 한 줄·예외)으로 바꾸고, 제품 코드에서 예외가 난 결함의 **QA 티켓에만** 붙인다.

```
pytest 출력 (쓰지 않음)                          티켓에 붙이는 형식
------------------------------------------      ----------------------------------------------------
    def apply_coupon(order_amount, ...):         Traceback (most recent call last):
        if current_amount is None:                 File "order_settlement/discount.py", line 63, in apply_coupon
            pass          ← 결함이 그대로 보임        return current_amount - discount
>       return current_amount - discount         TypeError: unsupported operand type(s) for -: ...
E       TypeError: unsupported operand ...
```

결과적으로 티켓 2,678건 중 419건(15.6%)에 스택트레이스가 있다.

### 4.3 실제 티켓 예시

결함: `order.change_status` (3.2의 LLM 결함)

| 작성자 | 제목 | 본문 |
|---|---|---|

## 6. 결함 위치 예측 모델 (F3-1, F3-3)

### 6.1 문제 정의

티켓 1건마다 대상 프로젝트의 함수 268개에 점수를 매겨 순위를 낸다 (순위 학습, Learning to Rank). 정답 함수가 몇 위에 오는지로 평가한다.

| 지표 | 의미 |
|---|---|
| Top-1 | 1위가 정답인 비율 |
| Top-3 | 정답이 3위 안에 있는 비율 (**KPI: 0.80 이상**) |
| MRR | 정답 순위의 역수 평균 (1위면 1, 2위면 0.5 …) |

동점은 불리하게 센다 (정답과 같은 점수인 후보가 모두 앞에 있다고 봄).

### 6.2 피처 (티켓 × 후보 함수 한 쌍마다)

| 피처 | 계산 | 혼합형에 사용 |
|---|---|---|
| `tfidf_sim` | 티켓 문장과 함수 소스(한글 docstring 포함)의 TF-IDF 유사도. 형태소 분석기 없이 문자 2~4-gram | O |
| `emb_sim` | bge-m3 임베딩 코사인 유사도 (파인튜닝 없음) | O |
| `trace_in` / `trace_last` / `trace_module` | 스택트레이스에 이 함수가 나오는지 / 예외가 난 위치인지 / 같은 모듈이 나오는지 | O |
| `loc`, `complexity` | 함수 줄 수, 분기 수 | O |
| `past_defects` | 학습 분할에서 이 함수에 있었던 결함 수 | **X (비교용만, 6.5)** |

### 6.3 모델 3종과 학습 절차

1. **① TF-IDF 단독**: `tfidf_sim` 순 (베이스라인)
2. **② 임베딩 단독**: `emb_sim` 순
3. **③ 혼합형**: XGBoost Ranker(`rank:ndcg`)가 위 피처를 종합

학습 절차 (평가 분할을 보고 모델을 고르는 누수를 막기 위해):

1. 하이퍼파라미터 8조합을 **학습 분할 안에서** 결함 단위 5-fold 교차검증으로 비교해 MRR이 가장 높은 것을 고른다 → `max_depth 4, n_estimators 400, learning_rate 0.05, min_child_weight 1`
2. 학습 분할 전체로 학습하고 평가 분할로 **한 번만** 평가한다 (주 결과)
3. 참고로 train+test 전체를 결함 단위·함수 단위 5-fold 교차검증으로도 평가한다

### 6.4 결과

**평가 분할 (티켓 524건)**

| 모델 | Top-1 | Top-3 | MRR |
|---|---|---|---|
| ① TF-IDF | 0.326 | 0.523 | 0.461 |
| ② 임베딩 (bge-m3) | 0.542 | 0.790 | 0.682 |
| **③ 혼합형** | **0.569** | **0.803** | **0.704** |
| ③-A 혼합형 + `past_defects` (비교용) | 0.611 | 0.845 | 0.738 |

**나눠 보기 (혼합형)**

| 구분 | n | Top-1 | Top-3 | MRR |
|---|---|---|---|---|
| 스택트레이스 있음 | 80 | 0.775 | 0.938 | 0.854 |
| 스택트레이스 없음 | 444 | 0.531 | 0.779 | 0.676 |
| AST 주입 | 336 | 0.607 | 0.845 | 0.737 |
| LLM 주입 | 188 | 0.500 | 0.729 | 0.644 |

**교차검증 Top-3 (train+test 2,638건)**

| 모델 | 결함 단위 5-fold | 함수 단위 5-fold (처음 보는 함수) |
|---|---|---|
| ① TF-IDF | 0.505 | 0.505 |
| ② 임베딩 | 0.783 | 0.783 |
| ③ 혼합형 | 0.805 | 0.774 |
| ③-A + `past_defects` | 0.820 | **0.263** |

읽는 법:

- **KPI(Top-3 ≥ 0.80)를 달성했다.** 다만 여유가 0.003이고, 524건 기준 95% 신뢰구간이 약 ±3.4%p라 다시 재면 0.80 아래로 나올 수도 있다. "목표 수준 달성"으로 보는 것이 정확하다.
- **과적합이 줄었다.** 학습 분할 Top-3 0.825, 평가 0.803으로 차이가 0.02다 (1차에는 0.165).
- **혼합형의 이점은 주로 스택트레이스가 있을 때 나온다.** 스택트레이스가 없으면 임베딩 단독(0.777)과 비슷하다(0.779).
- **LLM이 만든 결함이 더 어렵다** (Top-3 0.729 대 0.845). 업무 의미가 바뀐 결함은 증상 문장과 코드의 연결이 약하기 때문이다.
- **어려운 연산자:** SDL(문장 삭제), MCR(호출 제거). 무언가가 "빠진" 증상은 문장에서 위치가 잘 드러나지 않는다.
- **피처 중요도(gain):** 임베딩 0.720, TF-IDF 0.122, `trace_in` 0.076, `trace_module` 0.040, 나머지는 0.02 이하.

연산자별 표와 튜닝 결과 전체는 [eval/results/fault_localization.md](../eval/results/fault_localization.md)에 있다.

### 6.5 `past_defects`를 뺀 이유

"과거에 결함이 있었던 함수는 또 고장 나기 쉽다"는 PRD 6장의 피처다. 결함 단위 평가에서는 Top-3를 약 4%p 올린다.
그런데 함수 단위 교차검증(평가 함수를 학습에서 통째로 뺌)에서는 0.263으로 무너졌다.

원인: 이 데이터에서는 **모든 함수에 결함이 있다.** 그래서 모델이 "과거 결함이 있는 함수가 정답"이라고 배웠고, 처음 보는 함수(과거 결함 0)를 맨 뒤로 민다.
실제 운영에서는 결함 이력이 없는 함수가 대부분이므로, 주 모델에서 빼고 비교용(③-A)으로만 보고한다 (PRD 6장, 12장 반영).

학습 중에도 누수를 막는다. `past_defects`는 교차검증 fold마다 그 fold의 학습 부분 결함으로만 다시 세고, 학습 티켓은 자기 결함을 빼고 센다.

### 6.6 임베딩 모델 선택

PRD 12장의 미결 사항이었던 임베딩 모델을 1차 데이터로 비교해 **bge-m3**로 정했다.
UniXcoder는 평가 Top-3 0.066으로 무작위 수준이었다. 코드 전용 모델이라 한국어 티켓과 영어 코드를 연결하지 못한다.

## 7. 예측 도구 `predict_fault_location` (F3-2)

PRD 7.3 명세대로 `predict_fault_location(ticket_text, top_k=3)`을 만들었다 (`src/sr_agent/tools/predict.py`).

- 저장된 혼합형 모델 + TF-IDF + bge-m3로 함수 268개의 점수를 매기고 상위 k개를 돌려준다.
- 각 결과에 **SHAP 기여도**가 큰 피처 3개를 근거로 붙인다. SHAP 값의 합은 모델 점수와 정확히 일치한다(테스트로 확인).
- 티켓 본문에 traceback이 있으면 자동으로 스택트레이스 피처에 반영한다.
- 도구 규칙: 실패는 예외 대신 `{"error": ...}`, 입력 4,000자 이하·`top_k` 1~10, 함수 목록이 학습 때와 다르면 재학습을 요구한다.
- 모델은 처음 호출할 때 한 번만 올린다. 첫 호출은 약 21초(bge-m3 로딩), 이후는 약 0.25초다.

**S1 티켓으로 호출한 결과** — `"10만 원 이상 주문에 쿠폰을 두 장 쓰면 정산 금액이 음수로 찍힙니다."`

| 순위 | 함수 | SHAP 근거 (기여도) |
|---|---|---|
| 1 | `settlement.settle_order` | 함수 길이 20줄 (+0.567), 의미 유사도 0.626 (+0.212), … |
| 2 | `discount.round_down_won` | 분기 복잡도 1 (+0.175), 함수 길이 3줄 (+0.132), … |
| **3** | **`discount.apply_coupon`** (정답) | 단어 겹침 0.085 (+0.500), 분기 복잡도 3 (+0.032), … |

티켓이 "**정산** 금액"이라고 말하므로 증상이 드러나는 정산 함수가 1위로 나왔다. 실제 장애에서도 흔한 일이다.
그래서 **예측은 참고 자료로 쓰고, 최종 위치는 분석 에이전트가 근거(호출 관계·과거 이력·재현 테스트)로 정한다**는 원칙을 PRD v0.6에 반영했다.

## 9. 한계와 주의할 점

- **인공적인 결함이다.** AST 결함은 토큰 하나만 바꾼 것이고, LLM 결함도 함수 하나 안에서만 바뀐다. 여러 파일에 걸친 실제 결함과는 다르다.
- **함수 길이가 근거로 자주 나온다.** 긴 함수일수록 결함 후보가 많아 정답으로 자주 뽑힌 영향이다 (S1의 1위 근거가 "함수 길이"). 결함 주입 데이터의 편향이다.
- **티켓 문장은 LLM이 썼다.** 실제 현업 티켓보다 정돈되어 있고, 테스트 실패 정보에서 출발하므로 증상이 비교적 구체적이다.
- **KPI 여유가 작다** (0.803). 함수 단위 교차검증(0.774)을 함께 보여 주는 것이 정직하다.
- **후보는 원본 코드 기준이다.** 에이전트가 작업본을 고친 뒤 다시 예측해도 원본 기준 피처로 계산한다.

## 12. 다시 만들기

모든 단계는 시드가 고정돼 같은 입력이면 같은 결과가 나온다. LLM 응답은 파일로 저장돼 있어 다시 호출하지 않는다.

```powershell
.venv\Scripts\Activate.ps1
$env:PYTHONPATH = "src"

python -m sr_agent.datagen.llm_inject --workers 8   # LLM 결함 제안 (저장된 함수는 건너뜀)    약 $0.11
python -m sr_agent.datagen.inject --workers 6       # 결함 선별 (약 23분)
python -m sr_agent.datagen.tickets --workers 8      # 티켓 작성 (저장된 결함은 건너뜀)        약 $0.33
python -m sr_agent.datagen.split                    # 분할·누수 검사 (수 초)
python -m sr_agent.ml.train                         # 튜닝·학습·평가 (10~20분, 첫 실행은 임베딩 계산 추가)
```

- API 키는 `.env`의 `OPENAI_API_KEY`에서 읽는다 (`load_dotenv`).
- **대상 프로젝트 코드가 바뀌면** 결함의 원본 파일 해시가 달라지므로 `inject`부터 다시 돌려야 한다. 함수 목록이 바뀌면 예측 도구가 재학습을 요구한다.
- 테스트: `pytest tests` (168 passed, 약 1분 30초).

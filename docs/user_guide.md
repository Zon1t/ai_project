# RedFix 사용 설명서

> 대상: 운영 시스템을 유지보수하면서 SR(변경 요청)을 처리하는 개발자
> 화면 오른쪽 위 **?** 버튼을 누르면 이 문서를 화면 안에서 볼 수 있습니다. 각 영역 제목 옆의 **?** 아이콘에는 그 영역의 짧은 설명이 있습니다.

---

## 1. RedFix가 하는 일

SR 티켓 한 건을 받아 **원인 위치 찾기 → 수정안 작성 → 수정안 공격 → 코드로 판정**까지 자동으로 진행하고, 마지막 반영 여부는 담당자가 정합니다.

| 단계 | 하는 일 | 판단 주체 |
|---|---|---|
| 분석 | 결함 위치 예측 모델로 후보를 좁히고, 이력·규칙·호출 관계를 보고 원인 함수를 정한 뒤 재현 테스트를 작성 | LLM (근거 필수) |
| 수정 | 사내 규칙·과거 조치 이력을 근거로 원인 함수만 고침 | LLM |
| 공격 | 고친 코드를 경계값·빈 값·호출 경로 등 여러 관점에서 공격해 미달(덜 고침)·회귀(다른 동작을 깨뜨림)를 찾음 | LLM이 입력 제안 → 코드로 확인 |
| 판정 | 유형별 통과 조건을 코드로 검사 | **코드만** (LLM 판단 없음) |
| 승인 | 결과를 보고 반영하거나 반려 | **담당자** |

**하지 않는 일**
- 원본 코드를 직접 고치지 않습니다. 티켓마다 `runs/<티켓ID>/`에 복사본을 만들어 그 안에서만 작업합니다.
- 기존 테스트·기대 출력을 고치지 않습니다. 재현 테스트는 추가만 합니다.
- 여러 파일에 걸친 연쇄 수정, 요구사항 변경형 SR, 배포는 다루지 않습니다.

## 2. 시작하기

### 2.1 설치 (Windows PowerShell, 처음 한 번)

```powershell
uv venv .venv --python 3.12
.venv\Scripts\Activate.ps1
uv pip install -r requirements.txt
```

실시간 실행을 하려면 프로젝트 루트에 `.env` 파일을 만들고 키를 넣습니다. `.env`는 git에 올라가지 않습니다.

```
OPENAI_API_KEY=sk-...
```

처음 실행할 때 임베딩 모델(bge-m3, 약 2GB)을 내려받습니다. 유사 이력·사내 규칙 검색 색인이 없으면 한 번 만듭니다.

```powershell
$env:PYTHONPATH = "src"
python -m sr_agent.rag.index
```

### 2.2 화면 실행

```powershell
streamlit run app/streamlit_app.py
```

브라우저에서 http://localhost:8501 을 엽니다. 같은 네트워크의 다른 기기에서도 `http://<이 PC의 IP>:8501`로 접속됩니다 (`.streamlit/config.toml`의 `server.address = "0.0.0.0"`, 로그인 없음). 이 PC에서만 열려면 그 값을 `"localhost"`로 바꿉니다.

실시간 모드는 OpenAI API를 써서 비용이 듭니다. 다른 사람이 접속할 수 있게 열어 둘 때는 `.env`에 `REDFIX_LIVE_PASSWORD=<비밀번호>`를 넣고 화면을 다시 실행하세요. 실시간 모드에 들어갈 때 비밀번호를 묻습니다 (한 번 맞히면 그 브라우저 접속 동안 유지). 재생 모드는 비밀번호 없이 볼 수 있습니다.

### 2.3 두 가지 모드

| | 재생 | 실시간 |
|---|---|---|
| 하는 일 | 미리 실행해 저장한 결과(`data/replay/`)를 그대로 다시 보여 줌 | 티켓을 실제로 처리 (분석·수정·공격·판정) |
| 대상 티켓 | 재생 데이터가 있는 티켓 (시연 S1~S3) | 시연 티켓 + 화면에서 등록한 티켓 |
| API 호출·비용 | 없음 | 있음 (티켓당 보통 3~7분, $0.4~1) |
| "진행 과정 재생" / "실행" | 저장된 실행 로그를 같은 순서로 빠르게 재생 (약 10초) | 실제 진행 상황을 한 줄로 표시, 끝나면 단계별 요약 |
| 승인·반려 | 복사본(`runs/replay/`)에만 기록. **기록 초기화**로 되돌림 | 티켓 상태에 기록, `approved.diff` 생성 |
| 결과가 바뀌나 | 항상 같음 | LLM이 매번 조금씩 다르게 풂 (판정 기준은 같음) |
| 쓰는 때 | 화면 익히기, 발표·시연, 네트워크가 불안할 때 | 실제 SR 처리, 새 티켓 검증 |

실시간 실행은 중간에 멈춰도 단계마다 상태가 저장돼 다시 누르면 이어서 진행합니다. 처음부터 다시 하려면 **처음부터 다시**를 켭니다.
실시간으로 처리한 결과를 재생 데이터로 남기려면 `python -m sr_agent.ui save-replay <티켓ID>` (PYTHONPATH=src)를 실행합니다.

## 3. 티켓 등록 (실시간 모드)

사이드바 **새 티켓 등록**에서 유형을 고르고 제목·본문을 씁니다. 제목+본문은 4,000자까지입니다.

| 유형 | 언제 | 대상 함수 | 본문 작성 요령 |
|---|---|---|---|
| 결함 수정 | 동작이 틀렸을 때 | 비워 둠 (분석이 찾음) | **증상**을 씁니다: 어떤 입력·상황에서 무엇이 어떻게 틀렸는지. 예외가 났다면 traceback을 붙이면 위치 예측이 정확해집니다 |
| 코드 표준화 | 지원 종료 API 교체, 팀 스타일 적용 | **필수** (`모듈.함수`) | 바꿀 대상(예: `utcnow`, `pytz`)과 지킬 표준을 씁니다. 동작은 바뀌면 안 됩니다 |
| 보안 진단 조치 | 진단 도구가 지적한 약점 | **필수** (`모듈.함수`) | 진단 항목(예: SQL 문자열 결합)을 씁니다 |

좋은 결함 티켓 예:
> 10만 원 이상 주문에 쿠폰을 두 장 쓰면 정산 금액이 음수로 찍힙니다. 주문 120,000원, 정액 80,000원 쿠폰 + 정액 30,000원 쿠폰 조합에서 재현됩니다.

정답 함수 이름을 알고 있어도 결함 티켓에는 쓰지 않아도 됩니다. 분석 단계가 모델 예측과 근거로 찾습니다.

### 3.1 접수 검사 (v1.2)

**실행**을 누르면 분석 전에 접수 검사를 먼저 합니다. 다음이면 상태가 **보완 요청**이 되고 분석·수정을 하지 않습니다.

| 걸리는 경우 | 검사 |
|---|---|
| 본문이 너무 짧음(공백 제외 8자 미만)·같은 글자 반복 | 코드 (등록할 때 바로 알림) |
| 시스템 수정 요청이 아님 (잡담, 질문만, 무관한 요청) | LLM 판단 |
| 주문·정산 업무와 관련 없음 | LLM 판단 |
| 증상(요청) 문장이 없음 — LLM이 인용한 문장이 티켓에 글자 그대로 없으면 받지 않음 | LLM 인용 + 코드 확인 |
| 결함 수정인데 올바른 동작을 알 수 없음 | LLM 판단 |

화면에 부족한 정보가 나옵니다. 내용을 보충해 **새 티켓으로 등록**하세요.

## 4. 처리 화면 읽는 법

화면은 **위에서 아래로 결론 → 근거** 순서입니다. 대부분은 판정 결과와 한 줄 요약만 보고 판단할 수 있고, 필요할 때 아래를 펼칩니다.

### 4.1 진행 단계

`분석 › 수정 › 공격 › 판정 › 승인` 배지로 현재 위치를 보여 줍니다. 코드 표준화·보안은 진단이 위치를 알려 주므로 분석이 "생략"으로 표시됩니다.

실행·재생 중에는 지금 하는 일 한 줄만 보이고, 끝나면 **처리 과정** 요약이 펼쳐집니다.

실시간 **실행**은 서버에서 따로 돌아갑니다 (v1.2). 실행 중에 다른 티켓을 보거나, 버튼을 누르거나, 새로고침해도 멈추지 않습니다. 그 티켓을 다시 열면 진행 화면이 보이고, 끝나면 결과로 바뀝니다. 같은 티켓은 한 번에 하나만 실행되며, 다른 사람이 실행 중이면 실행 버튼 대신 진행 화면이 보입니다. 서버를 끄면 실행도 멈춥니다 (다시 실행하면 끝난 단계부터 이어서 합니다).

### 4.2 판정 결과

제목에 **판정 통과 / 조건부 통과(미평가 n개) / 실패**와 시도 차수가 나오고, 그 아래 한 줄로 요약합니다.

- **재시도**: 판정 실패 후 다시 고친 횟수 (상한 3회, 넘으면 사람 검토)
- **공격이 제기한 문제 n건 → 판정이 다시 실행해 실제 문제 m건**: 공격 에이전트는 문제가 될 만한 입력을 *제기*만 합니다. 판정이 같은 입력을 직접 다시 실행해 정답 구현(표준화는 원본)과 다를 때만 실제 문제로 셉니다. 정답 구현이 없는 새 티켓은 자동 재확인을 못 하므로 공격 로그에서 직접 봅니다

### 4.3 판정 조건

실패한 조건은 빨간 상자로 바로 보이고, 나머지는 **판정 조건 보기**를 펼치면 묶음별로 나옵니다. 조건마다 **무엇을 확인하는지**와 **결과**가 함께 나옵니다. 유형에 따라 조건이 다릅니다.

| 묶음 | 조건 | 결함 수정 | 코드 표준화 | 보안 |
|---|---|---|---|---|
| 티켓 | 접수 검사 통과, 티켓 증상과 재현 테스트 연결 | ✓ ✓ | ✓ | ✓ |
| 재현 테스트 | 원본에서 실패, 수정본에서 통과 | ✓ ✓ | | |
| 기존 동작 | 기존 테스트 통과, 변경 범위(대상 함수만) | ✓ ✓ | ✓ ✓ | ✓ ✓ |
| 정답·원본과 비교 | Hypothesis 200개 입력에서 정답 구현(표준화·보안은 원본)과 동일, 공격 입력 무력화(보안) | ✓ | ✓ | ✓ ✓ |
| 공격 결과 재확인 | 공격 에이전트가 만든 입력을 판정이 다시 실행해 정답(표준화는 원본)과 비교 | ✓ | ✓ | ✓ |
| 규칙 검사 | 지원 종료 API 0건, 팀 스타일 0건 / 보안 위반 0건 | | ✓ ✓ | ✓ |

예: S1의 `6/6` = 재현 테스트 2개 + 기존 테스트 + 변경 범위 + 정답 비교(Hypothesis) + 공격 결과 재확인. 공격은 이 중 한 항목이고, 공격 에이전트가 "문제없다"고 판단해서가 아니라 **판정이 그 입력을 직접 다시 실행해** 정답과 같은지 본 결과입니다.

| 아이콘 | 뜻 |
|---|---|
| 초록 체크 | 통과 |
| 빨간 X | 실패 — 재시도 입력으로 수정 에이전트에 전달됨 |
| 회색 | **미평가** — 이 티켓에는 검사할 기준이 없어 확인하지 못함 (6장 참고) |

### 4.4 탭 4개

| 탭 | 볼 것 |
|---|---|
| 결함 위치 | 모델 예측 Top-3(참고 자료)와 에이전트의 최종 판단을 나란히. 모델 1위와 다르게 골랐으면 그 이유. 에이전트가 인용한 **티켓 증상**과 그것을 확인하는 재현 테스트 단언. 재현 테스트가 원본에서 실패했는지. **이 함수의 현재 코드(수정 전)**. 예측 점수는 확률이 아니라 후보끼리 순서를 정하는 상대값이라 음수일 수 있습니다. 점수는 SHAP 근거 상세에만 보입니다. **예측 신호 낮음** 경고는 1위 점수·의미 유사도가 평가 티켓의 하위 1%보다 낮다는 뜻입니다 (학습한 티켓 분포 밖) |
| 근거 | 인용한 사내 규칙(규칙 ID·좋은 예)과 과거 장애·조치 이력 |
| 패치 diff | 대상 함수의 **수정 전/후 전체 코드**. **나란히**(좌우 비교)와 **바뀐 줄 표시**(한 화면, 초록 + 추가·빨강 - 삭제) 중 고름. 같은 파일의 import 변경, 파일 diff 원문. 시도가 여러 번이면 시도별로 고를 수 있음 |
| 공격 로그 | 공격이 제기한 입력마다 **판정 결과**(실제 문제 / 문제 아님 / 미평가)와 공격의 주장(미달·회귀), 수정본·원본 결과. 관점별 라운드 결과. 라운드 수: 첫 시도는 3관점(경계값·타입·빈 값·호출부 경로), 재시도는 이전에 실제 문제를 찾았던 관점 + 아직 안 쓴 관점(조합·순서, 성질 기반)으로 3관점. 이전 시도의 공격 입력은 판정이 모두 다시 실행합니다 |

### 4.5 시연 케이스 (실시간 모드)

사이드바 **시연 케이스 불러오기**에서 A~D를 고르면, 판단 연습용 티켓이 등록됩니다.

| 케이스 | 내용 |
|---|---|
| A~C | 학습·이력에 없는 결함을 심은 코드로 처리합니다. 결함 때문에 실패하는 기존 테스트는 에이전트와 판정에서 숨깁니다 |
| D | 정답 구현이 없는 새 보안 티켓 (현업과 같은 상황) |

화면 위 상자의 **확인할 것**을 따라 보고 승인·반려한 뒤, 맨 아래 **정답 확인**을 누르면 숨긴 테스트를 패치에 돌려 판단이 맞았는지 알려 줍니다.
**처음부터 다시**를 켜고 실행하면 결함 버전부터 새로 만듭니다.

---

### 4.6 결과 삭제 (실시간 모드)

- 티켓 하나: 실행 버튼 줄 오른쪽 끝 **삭제** → 확인 창에서 **삭제**(닫거나 **취소**하면 아무것도 지우지 않음) → 작업본·상태·실행 로그(`runs/<티켓ID>*`)를 지웁니다. 화면에서 등록·불러온 티켓은 "티켓도 목록에서 삭제"를 고를 수 있습니다 (S1~S3는 목록에 고정).
- 여러 개: 사이드바 **결과 정리**에서 골라 한 번에 지웁니다. 실행하지 않은 등록 티켓도 목록에서 뺄 수 있습니다.
- 실행 중인 티켓은 지울 수 없습니다. 재생 모드의 저장 데이터(`data/replay`)는 지우지 않습니다.

## 5. 승인·반려 기준

**승인 후 반영**은 판정을 통과한 티켓에서만 눌립니다. 승인하면 마지막 패치가 `runs/<티켓ID>/approved.diff`로 확정됩니다. 실제 저장소 반영(커밋·배포)은 이 diff로 직접 합니다.

승인 전 확인 목록:
1. **패치 diff**: 대상 함수만 바뀌었는지, 의도와 다른 부분이 없는지
2. **근거**: 인용한 규칙이 이 SR에 맞는 규칙인지
3. **판정 조건의 회색(미평가) 항목**: 자동으로 확인하지 못한 부분을 직접 봤는지
4. **재현 테스트**(결함 수정): 기대값이 업무 규칙과 맞는지. 재현 테스트가 틀리면 틀린 수정도 통과할 수 있습니다

반려할 때는 **반려 → 사유 입력 → 반려 확정**을 누릅니다. 사유는 티켓 상태에 남습니다.

## 6. 자동 검증의 한계 (꼭 읽어 주세요)

판정은 코드가 하지만, **무엇과 비교할지**가 있어야 엄격하게 검사할 수 있습니다.

| 상황 | 자동으로 확인하는 것 | 확인하지 못하는 것 |
|---|---|---|
| 시연·평가 티켓 (정답 구현이 준비됨) | 재현 테스트, 기존 테스트, 변경 범위, Hypothesis 200개 입력과 공격 입력 전부에서 정답과 동일 | — |
| **새로 등록한 결함 티켓** (정답 구현 없음) | 재현 테스트(원본 실패·수정본 통과), 기존 테스트, 변경 범위 | 정답과의 비교, 공격 입력 재판정 → **회색(미평가)**. 공격이 찾은 입력은 공격 로그에서 직접 확인 |
| 새로 등록한 코드 표준화·보안 티켓 | 지원 종료 API·스타일·보안 규칙 0건, 기존 테스트, 변경 범위, 공격 입력에서 원본과 동일(표준화) | Hypothesis 동작 보존 비교(입력 생성 규칙이 없음) |

즉 새 결함 티켓에서는 **재현 테스트의 기대값이 맞는지가 품질을 좌우**합니다. 분석 에이전트는 사내 규칙(BIZ-*)으로 기대값을 정하도록 되어 있지만, 규칙이 없는 업무는 사람이 확인해야 합니다.

### 처음 보는 결함·새 코드에도 동작하나요?

- **같은 프로젝트의 새 결함**: 예. 결함 위치 예측 모델은 특정 결함 패턴을 외운 것이 아니라 티켓-코드 유사도, 스택트레이스, 함수 길이·복잡도로 점수를 매기므로 학습 때 없던 결함에도 씁니다. 함수가 추가·삭제돼도 그대로 예측하고, 새 함수에는 표시가 붙습니다. 예측은 참고 자료이고, 최종 위치는 분석 에이전트가 코드·호출 관계·재현 테스트로 정합니다.
- **예측이 틀릴 때**: 분석 에이전트는 Top-3 밖의 함수도 고를 수 있고, 그때는 근거를 남깁니다. 평가에서 모델 Top-3 적중 85%, 에이전트 최종 위치 정답 100%였습니다(홀드아웃 20건).
- **다른 프로젝트**: 대상 프로젝트(`target/`)를 바꾸면 사내 규칙(`data/rules/rules.json`)과 과거 이력 색인을 그 프로젝트에 맞게 다시 만들어야 근거 검색이 의미가 있습니다. 결함 위치 모델은 재학습을 권장합니다(`python -m sr_agent.ml.train`).

## 7. 사람 검토로 넘어간 경우

상태가 **사람 검토**이면 자동 처리를 멈춘 것입니다. 화면 위쪽 경고에 사유가 나옵니다.

| 사유 | 뜻 | 대응 |
|---|---|---|
| 분석 확신 불가 | 분석 에이전트가 티켓 증상과 원인 함수를 근거로 잇지 못해 수정하지 않음 (증상 불명확, 규칙 없음, 여러 함수에 걸침 등) | 사유를 보고 재현 조건·기대 동작을 보충해 다시 등록 |
| 분석 실패: 재현 테스트를 작성하지 않음 / 원본에서 통과함 | 결함을 드러내는 테스트를 만들지 못함 | 티켓에 재현 조건(입력값)을 더 구체적으로 적어 다시 등록 |
| 분석 실패: 기대값이 업무 규칙과 다름 | 재현 테스트의 기대값이 올바른 코드에서도 틀림 | 관련 업무 규칙이 KB에 있는지 확인. 없으면 규칙 추가를 검토 |
| 판정 실패 4회 (재시도 상한 초과) | 네 번 고쳐도 판정 통과 못함 | 공격 로그·판정 조건에서 반복해서 걸린 입력을 보고 직접 수정 |
| BudgetExceeded | 티켓당 토큰 상한 초과 | 티켓 범위를 나눠 다시 등록 |
| LLMRefusal / LLMError | 모델 거부·장애·API 시간 초과 | 잠시 뒤 **처음부터 다시** 켜고 재실행 |

**API 크레딧이 소진되면** 진행 막대가 "OpenAI API 크레딧(사용 한도) 소진"으로 멈춥니다. 이때는 사람 검토로 넘기지 않고 상태를 그대로 둡니다. [OpenAI 결제 화면](https://platform.openai.com/settings/organization/billing/)에서 충전한 뒤 같은 티켓을 다시 **실행**하면 끝난 단계부터 이어서 진행합니다 (처음부터 다시는 켜지 않습니다).

## 8. 자주 묻는 것

**Q. 실행 중에 창을 닫으면?**
상태가 단계마다 `runs/<티켓ID>/state.json`에 저장됩니다. 다시 실행하면 끝난 단계는 건너뜁니다. 처음부터 하려면 **처음부터 다시**를 켜고 실행합니다.

**Q. 실행 기록은 어디 있나요?**
`runs/<실행ID>.jsonl`에 LLM·도구 호출, 토큰, 소요 시간이 남습니다. 화면에서는 **처리 과정 → 원본 실행 로그 보기**로 봅니다.

**Q. 원본 코드가 바뀌지 않았다는 걸 어떻게 아나요?**
수정은 `runs/<티켓ID>/work/`에서만 하고, 판정의 "변경 범위" 조건이 대상 함수·import 외 변경을 막습니다.

**Q. 명령줄로 돌릴 수 있나요?**

```powershell
$env:PYTHONPATH = "src"
python -m sr_agent.run --ticket SR-2041 [--restart]
python -m eval.run_e2e --split holdout          # 평가용 홀드아웃 20건 일괄
```

**Q. OneDrive 폴더에서 테스트가 접근 거부로 실패해요.**
OneDrive 폴더는 디렉터리에 읽기 전용 속성이 붙습니다. 작업본 삭제 시 속성을 풀고 지우도록 처리되어 있습니다. git이 줄바꿈을 CRLF로 바꿔 받으면 결함 데이터 해시가 맞지 않으므로, 이 저장소는 `git config core.autocrlf false`로 둡니다.

## 2. 판정: 공격 입력 재실행 (F5-4)

판정 조건 `attack_findings_rechecked`를 세 유형에 넣었다.

- 공격 에이전트가 낸 입력을 **확인 여부와 관계없이 전부** 다시 실행한다. LLM이 적은 기대값과 "미달·회귀" 라벨은 쓰지 않는다.
- 비교 기준: 결함 수정·보안은 정답 구현, 코드 표준화는 원본. 정답 기준이면 원본도 정답과 달랐던 입력 = 미달, 원본은 맞았던 입력 = 회귀로 다시 분류한다.
- 실행할 수 없는 입력(JSON·형식 오류, 없는 함수)은 세지 않고 개수만 적는다.
- 실패한 입력(최대 5개: 입력·분류·수정본·원본, **정답 출력 제외**)을 재시도하는 수정 에이전트에 넘긴다.
- E2E처럼 Hypothesis 입력 생성 규칙이 없어도, 정답 구현만 있으면 공격 입력으로 불완전 패치를 잡는다.

LLM은 입력만 제안하고 맞고 틀림은 코드가 정한다 (CLAUDE.md 규칙 4). S1·S3 실제 실행에서 공격 에이전트가 "회귀"·"미달"로 보고한 입력(예외 메시지만 다른 비정상 입력, 음수 금액 입력)을 판정이 정답과 같다고 확인해 통과시켰다.

## 3. 공격: 관점별 라운드 (F5-3, F4-3)

| 설정 (`config.py`) | 값 |
|---|---|
| `ATTACK_ROUNDS` | 3 (수정 시도 1회당) |
| `ATTACK_ROUNDS_WITH_HISTORY` | 5 (이 티켓의 이전 시도가 판정에서 실패한 재시도) |
| `ATTACK_PARALLEL` | 3 (동시 실행 묶음 크기) |
| `ATTACK_MAX_TURNS` | 16 (라운드 하나의 턴 상한. 12에서는 S1 라운드 2개가 회귀 확인 전에 상한에 걸림) |
| `ATTACK_ANGLES` | 경계값 → 타입·빈 값 → 호출부 경로 → 조합·순서 → 성질 기반 |

- **라운드** = 관점 하나를 맡은 공격 에이전트 1회 실행 (대화가 따로). **턴** = 라운드 안의 LLM 호출.
- 라운드 수를 늘리는 조건은 판정 실패(재시도) 하나다. 처음에는 "같은 함수의 공격 이력"도 조건이었으나, 이력에 오탐이 섞이면 라운드만 늘어나 뺐다. 이력은 각 라운드가 먼저 검색해 재사용한다 (F4-3).
- 여러 라운드가 같은 입력을 내면 하나만 남기고, 어느 관점이 찾았는지 기록한다.
- 동시 실행 대비: 토큰 예산 합산, 커버리지 측정 캐시, 공격 이력 접근에 잠금. 라운드별 로그 줄에 관점(`angle`)을 붙인다.
- 공격 이력은 판정 뒤에 저장한다. 판정이 정답(표준화는 원본)과 다르다고 확인한 입력만 남긴다. 정답 구현이 없어 판정이 비교하지 못했으면 코드로 확인된 발견을 남긴다.
- `--attack-rounds N` 실행 옵션으로 라운드 수를 고정할 수 있다 (측정용).

python -m eval.run_ablation --report-only    # 결과 파일로 표만 다시 씀

### 5.3 해석

- **공격 단계**: 판정 통과 기준 해결률 +10%p(2건). 토큰은 약 2배, 시간은 1.5배. 회귀 누출은 줄지 않았다 (5.4).
- **예측 도구**: 이 20건에서는 해결률 효과가 없다. 예측 없이도 에이전트가 위치를 모두 맞혔고, 분석 턴이 평균 2회 줄어든 정도다. 20건에서 1건 = 5%p라 차이를 판단하기 어려운 표본이다. 결함 위치 모델 자체(Top-3 0.803)는 목표를 달성했다.
- **실패 유형**: 해결하지 못한 티켓은 대부분 분석 단계에서 재현 테스트 기대값을 업무 규칙과 맞추지 못한 경우다. `shipping.decide_return_fee_payer`는 세 조건 모두 실패했다.
- 재시도로 통과한 티켓이 생겼다 (전체 기능에서 2회째·3회째 통과 각 1건). PRD 12장 "재시도 횟수" 판단 자료다.

### 5.4 회귀 누출 원인

`review.can_write_review`(전체 기능, 3회째 통과 후 숨긴 테스트 2건 실패):

1. 1회째: 공격이 "배송일 없음" 입력을 냈고, 판정이 정답과 다르다고 확인해 실패시켰다.
2. 2·3회째: 수정 에이전트가 그 입력에서 원본 동작을 유지하는 쪽으로 고쳤다.
3. 3회째 공격 라운드는 1회째 입력을 다시 내지 않았고, 판정은 그 시도의 공격 입력만 다시 실행하므로 통과했다.
4. 숨긴 테스트에서 바로 그 입력이 실패했다.

E2E에는 Hypothesis 입력 생성 규칙이 없어, 판정이 볼 수 있는 입력이 그 시도의 공격 입력뿐이라 생긴 빈틈이다.
→ 다음 작업: 판정이 **이전 시도의 공격 입력까지 누적해** 다시 실행한다.
